## Overview

The HTTP Call Node allows you to make an HTTP call to a specified URL with a given method, headers, and body. This node is particularly useful when you need to interact with external APIs or services.

The HTTP Call Node uses the Fetch API to make HTTP requests. It supports all HTTP methods (GET, POST, PUT, DELETE, etc.) and allows you to specify custom headers and a request body.

:::caution
When using the default [browser executor](../user-guide/executors.md), you have to worry about [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) when making HTTP requests to external APIs. If the API you are trying to call does not support CORS to `http://tauri.local` (most do not), you will run into CORS problems. This can manifest as an error `fetch failed` in the output panel.

This can be worked around by using the [Node executor](../user-guide/executors.md) in Rivet, which does not do CORS checks.
:::

## Example 1: Make a GET request to an API

1. Create an HTTP Call Node and set the `Method` to `GET` and the `URL` to `https://jsonplaceholder.typicode.com/todos/1`.
2. Run the graph. You should see all of the response data, such as the headers, response code, and body, in the output panel.

![HTTP Call Node Example 1](./assets/http-call-node-example-01.png)

## Example 2: Make a POST request to an API

1. Create an HTTP Call Node and set the `Method` to `POST` and the `URL` to `https://jsonplaceholder.typicode.com/posts`. Enable the "Use Input" toggle on the "Body" setting to enable the input port for Body.
2. Create an [Object Node](./object.mdx) and set the object to:

```json
{
  "title": "foo",
  "body": "bar",
  "userId": 1
}
```

3. Create a [To JSON Node](./to-json.mdx) and connect the Object Node to the `Data` input of the To JSON Node. Connect the To JSON Node to the `Body` input of the HTTP Call Node.
4. Create an [Extract Object Path](./extract-object-path.mdx) Node and connect the `JSON` output of the HTTP Call Node to the `Object` input of the Extract Object Path Node. Set the `Path` to `$.id`.
5. Run the graph. You should see the created ID of the post in the Extract Object Path Node's output panel.

![HTTP Call Node Example 2](./assets/http-call-node-example-02.png)

## Interactive authentication

Rivet desktop can authenticate through Google using a dedicated Chrome/Chromium window and capture the JWT returned by your platform. Your platform does not need to change its callback implementation.

Configure these fields on the HTTP Call node:

- **OAuth login URL**: the page to open after HTTP 401 or 403. Both statuses use the same authentication and Bearer-token retry flow. Without a configured URL or a response `Location`, the error remains a normal response; Rivet does not navigate to the protected API as a login page.
- **OAuth callback URL**: the platform endpoint returning the token JSON. If omitted, Rivet reads `redirect_uri` from the login/authorization URL. Match the exact callback origin and path; OAuth `code` and `state` query parameters may vary.

For example, a login URL like `https://auth.example.com/login?response_type=code&client_id=CLIENT_ID&redirect_uri=https%3A%2F%2Fapi.example.com%2Fapi%2Fv1%2Faccess_tokens%2Fcallback&identity_provider=Google` uses `https://api.example.com/api/v1/access_tokens/callback` as its callback.

HTTP 302 responses pointing to recognizable OAuth authorization pages use their `Location` URL. Rivet inspects desktop redirects before following them, so provider CORS restrictions do not hide the login redirect.

Complete sign-in in the Chrome window. Rivet reads only the configured top-level callback response, expecting:

```json
{
  "data": {
    "access_token": "<jwt>",
    "expires_in": 3600,
    "user": { "email": "<email>" }
  }
}
```

Rivet extracts `data.access_token`, closes the dedicated browser, and retries the original method, URL, headers, and body once with `Authorization: Bearer <jwt>`. This works with both the desktop browser executor and Node executor. A second authentication failure does not open another window. Ordinary cross-origin redirects strip the Authorization header.

The desktop app reuses tokens in memory for the same open project across graph executions, including after graph edits. Cache entries are separated by API origin, login/callback settings, token source, and configured Authorization header. A token is reused until its supplied lifetime ends or the API rejects it; rerunning does not extend its lifetime. Without a supplied lifetime, the token remains available until rejected or the project session closes. Concurrent nodes share one login. Closing a project or quitting the app clears its credentials; the in-memory session cache is not serialized into project files or settings. The Node executor scopes sessions to the connected debugger client and clears them on disconnect or when the desktop reports that the project was closed.

Closing the login window cancels authentication and preserves the original response. Cancelling one waiting node does not interrupt others using the same login; cancelling all waiting nodes closes the helper and browser. Cancelling a run does not discard an already authenticated project session.

Chrome/Chromium must be installed. Set `RIVET_CHROME_PATH` to an absolute executable path if auto-detection cannot find it. Rivet uses a temporary profile, separate from your normal browser profile, and a private debugging pipe. The temporary profile is removed after sign-in, cancellation, or failure. Sign-in times out after ten minutes.

If the platform callback fails or returns invalid JSON/token data, Rivet reports the error and leaves Chrome open with the original response for inspection. Close that Chrome window when finished to clean up the helper and temporary profile. Callback bodies and JWTs are not printed to logs.

Rebuild Rivet's bundled executor sidecar after updating this code (`yarn workspace @ironclad/rivet-app-executor build`); the desktop app launches its new `--oauth-login` mode for both executors. Google login runs in a full browser because Google prohibits embedded user agents.

The web UI outside Tauri keeps non-interactive Fetch behavior. Embedded hosts can provide `requestHttpAuthentication` in process context or processor options and return `{ accessToken, expiresIn? }`, or `false` on cancellation. Hosts can also provide `httpRequest`, a transport supporting manual redirects. The protected API remains responsible for validating the JWT.

### Official login pages and Authorization headers

A login page such as `https://dev.admin.getenter.ai/login` can be used without a JSON callback. Leave **OAuth callback URL** empty and use a login URL without `redirect_uri`. Rivet watches requests made by that browser tab and captures a Bearer JWT only from a request to the same origin as the protected API, after a successful response. Google requests, unrelated origins, expired tokens, and unsuccessful API responses are ignored. If necessary, navigate within the signed-in app to a page that calls the configured API. The JWT's `exp` claim controls its cached lifetime when available.

The Enter plugin uses this header-capture flow with **Settings → Enter → OAuth login URL**, including for all requests previously authenticated with `blackPearlApiKey`. It does not require **OAuth callback URL**.

### Using authentication from plugins

Plugins can call the injected `rivet.fetchWithHttpAuthentication(url, init, context, options)` helper with `loginUrl` and optional `callbackUrl`. Set `tokenSource: 'authorization-header'` for official login pages, or `tokenSource: 'callback'` for JSON callbacks. Without an explicit source, a callback URL or `redirect_uri` selects JSON capture; otherwise header capture is used. Set `preferCachedToken: true` when a cached OAuth token should replace the plugin's configured API-key Authorization header on subsequent requests. The default preserves explicit Authorization headers. Set `authenticateBeforeRequest: true` to sign in before sending the request when there is no reusable session; cancellation or a missing interactive host prevents the request.

The updated Enter plugin uses this helper for all Black Pearl API requests from **Deploy Project**, **Data Fetcher V1**, **Fetch Input**, **Talisman LLM**, and **Intelligence**. Configure its **OAuth login URL** under **Settings → Enter**. When the API key is missing, empty, or whitespace-only and no JWT is available, it signs in before making the request. Nodes and later runs of the same open project share the JWT. An already OAuth-capable plugin can use this session behavior without another plugin release; install the updated Rivet desktop app and executor sidecar.

Embedded hosts and SDK callers can supply `httpAuthenticationCache` in process context or processor options to retain authentication across runs. For example, create an in-memory `HttpAuthenticationSessions` instance and pass `sessions.forProject(project.metadata.id)` to each processor for that open project. Call `sessions.retain(openProjectIds)` when projects close and `sessions.clear()` when the host session ends. Without a host-provided cache, the helper falls back to the graph's execution cache, preserving execution-only behavior.

## Error Handling

The HTTP Call Node will error if the HTTP request fails for any reason, such as a network error or if the server returns an error status code. If the `Error on non-200 status code` setting is enabled, the node will also error if the status code of the HTTP response is not 200.

## FAQ

**Q: Can I use the HTTP Call Node to make requests to any API?**

A: Yes, you can use the HTTP Call Node to make requests to any API that supports the HTTP methods GET, POST, PUT, or DELETE.

**Q: Can I use the HTTP Call Node to send JSON in the request body?**

A: Yes, you can use a [Text Node](./text.mdx) to create a JSON string and connect it to the `Body` input of the HTTP Call Node.

**Q: Can I use the HTTP Call Node to handle API authentication?**

A: Yes, you can include authentication headers in the `Headers` input of the HTTP Call Node. However, for security reasons, you should not hardcode sensitive information like API keys in your graphs. Instead, consider using a [Context Node](./context.mdx) to securely pass in sensitive information from the host application.
